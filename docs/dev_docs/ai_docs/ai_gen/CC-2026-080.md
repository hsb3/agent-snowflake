# Enhanced Context Schema Guide

This document explains the `EnhancedContextSchema` configuration used by `graph_enhanced` and `graph_minimal` in `graph2.py`.

## Overview

`EnhancedContextSchema` extends the base `ContextSchema` with middleware-specific configuration parameters. It allows you to control all middleware behavior through:

1. **LangGraph Studio UI** - Configure when creating assistants
2. **Environment variables** - Set at deployment time
3. **Runtime context** - Pass via `graph.invoke(..., context={...})`

## Quick Reference

### Middleware Mode

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `middleware_mode` | str | `"enhanced"` | Overall mode: `enhanced` (all), `minimal` (limits+retry), `none` |

**Note:** Currently this field is informational. Middleware is controlled by individual enable flags below.

## Configuration Sections

### 1. Human-in-the-Loop

Require human approval before executing SQL queries.

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `enable_hitl` | bool | `true` | Enable HITL for `sql_db_query` tool |
| `hitl_allowed_decisions` | str | `"approve,edit,reject"` | Comma-separated allowed decisions |

**Important:**
- HITL only activates when `read_only=false`
- Requires a checkpointer (automatically configured)
- User can approve, edit query, or reject

**Environment variables:**
```bash
SNOWFLAKE_AGENT_ENABLE_HITL=true
SNOWFLAKE_AGENT_HITL_ALLOWED_DECISIONS=approve,edit,reject
```

**Example usage:**
```python
# Disable HITL
context = {"enable_hitl": false}
result = graph_enhanced.invoke({"messages": [...]}, context=context)
```

### 2. Model Call Limits

Prevent runaway agents from making too many LLM calls.

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `model_call_thread_limit` | int | `10` | Max calls across entire thread (0=unlimited) |
| `model_call_run_limit` | int | `5` | Max calls per single run (0=unlimited) |
| `model_call_exit_behavior` | str | `"end"` | Behavior: `end` (graceful) or `error` (exception) |

**Behavior:**
- `thread_limit`: Persists across the entire conversation (thread)
- `run_limit`: Resets with each new user message
- Set to `0` to disable that limit

**Environment variables:**
```bash
SNOWFLAKE_AGENT_MODEL_CALL_THREAD_LIMIT=10
SNOWFLAKE_AGENT_MODEL_CALL_RUN_LIMIT=5
SNOWFLAKE_AGENT_MODEL_CALL_EXIT_BEHAVIOR=end
```

**Example usage:**
```python
# Allow more calls for complex queries
context = {
    "model_call_thread_limit": 20,
    "model_call_run_limit": 10
}
```

### 3. Tool Call Limits (Global)

Control tool usage across all tools.

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `tool_call_thread_limit` | int | `20` | Max tool calls (all tools) across thread |
| `tool_call_run_limit` | int | `10` | Max tool calls (all tools) per run |
| `tool_call_exit_behavior` | str | `"continue"` | Behavior: `continue`, `end`, or `error` |

**Exit behaviors:**
- `continue`: Block exceeded calls but let agent continue with error message
- `end`: Stop execution immediately with final message
- `error`: Raise exception

**Environment variables:**
```bash
SNOWFLAKE_AGENT_TOOL_CALL_THREAD_LIMIT=20
SNOWFLAKE_AGENT_TOOL_CALL_RUN_LIMIT=10
SNOWFLAKE_AGENT_TOOL_CALL_EXIT_BEHAVIOR=continue
```

### 4. Tool Call Limits (sql_db_query specific)

Extra limits specifically for the expensive `sql_db_query` tool.

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `sql_query_thread_limit` | int | `10` | Max SQL queries across thread |
| `sql_query_run_limit` | int | `5` | Max SQL queries per run |

**Note:** These limits are in addition to global tool limits and use the same `tool_call_exit_behavior`.

**Environment variables:**
```bash
SNOWFLAKE_AGENT_SQL_QUERY_THREAD_LIMIT=10
SNOWFLAKE_AGENT_SQL_QUERY_RUN_LIMIT=5
```

**Example usage:**
```python
# Allow more queries for data exploration
context = {
    "sql_query_thread_limit": 25,
    "sql_query_run_limit": 10
}
```

### 5. Model Retry Configuration

Automatically retry failed model calls with exponential backoff.

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `retry_max_retries` | int | `3` | Max retry attempts after initial call |
| `retry_backoff_factor` | float | `2.0` | Exponential backoff multiplier |
| `retry_initial_delay` | float | `1.0` | Initial delay in seconds |
| `retry_max_delay` | float | `60.0` | Maximum delay between retries |
| `retry_jitter` | bool | `true` | Add ±25% random jitter to delays |

**Retry schedule (with defaults):**
- Attempt 1: Immediate
- Attempt 2: Wait 1s
- Attempt 3: Wait 2s
- Attempt 4: Wait 4s

**Environment variables:**
```bash
SNOWFLAKE_AGENT_RETRY_MAX_RETRIES=3
SNOWFLAKE_AGENT_RETRY_BACKOFF_FACTOR=2.0
SNOWFLAKE_AGENT_RETRY_INITIAL_DELAY=1.0
SNOWFLAKE_AGENT_RETRY_MAX_DELAY=60.0
SNOWFLAKE_AGENT_RETRY_JITTER=true
```

**Example usage:**
```python
# More aggressive retry for flaky network
context = {
    "retry_max_retries": 5,
    "retry_backoff_factor": 1.5,
    "retry_initial_delay": 0.5
}
```

### 6. Summarization

Automatically compress conversation history when token limits are reached.

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `enable_summarization` | bool | `true` | Enable automatic summarization |
| `summarization_model` | str | `"gpt-4o-mini"` | Model for generating summaries |
| `summarization_trigger_tokens` | int | `4000` | Token count to trigger summarization |
| `summarization_keep_messages` | int | `20` | Recent messages to preserve verbatim |

**How it works:**
1. Monitors token count in conversation
2. When exceeds trigger threshold, summarizes older messages
3. Preserves most recent N messages unmodified
4. Summary inserted as single message

**Environment variables:**
```bash
SNOWFLAKE_AGENT_ENABLE_SUMMARIZATION=true
SNOWFLAKE_AGENT_SUMMARIZATION_MODEL=gpt-4o-mini
SNOWFLAKE_AGENT_SUMMARIZATION_TRIGGER_TOKENS=4000
SNOWFLAKE_AGENT_SUMMARIZATION_KEEP_MESSAGES=20
```

**Example usage:**
```python
# Disable for short conversations
context = {"enable_summarization": false}

# Or customize for long exploration
context = {
    "summarization_trigger_tokens": 8000,  # More lenient
    "summarization_keep_messages": 30      # Preserve more
}
```

### 7. Todo List

Enable task planning and tracking for complex multi-step analysis.

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `enable_todo` | bool | `true` | Enable todo list middleware |

**What it does:**
- Adds `write_todos` tool to agent
- Provides system prompt encouraging task planning
- Agent can break down complex requests into subtasks

**Environment variable:**
```bash
SNOWFLAKE_AGENT_ENABLE_TODO=true
```

**Example usage:**
```python
# Disable for simple queries
context = {"enable_todo": false}
```

### 8. Model Fallback

Automatically switch to backup models when primary fails.

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `enable_fallback` | bool | `true` | Enable automatic model fallback |
| `fallback_models` | str | `""` | Comma-separated fallback models (empty=auto) |

**Auto-detection (when `fallback_models` is empty):**
- Primary: `gpt-4o*` → Fallbacks: `gpt-4o-mini`, `claude-3-5-sonnet-20241022`
- Primary: `claude-*` → Fallbacks: `gpt-4o`, `gpt-4o-mini`
- Other → Fallback: `gpt-4o-mini`

**Environment variables:**
```bash
SNOWFLAKE_AGENT_ENABLE_FALLBACK=true
SNOWFLAKE_AGENT_FALLBACK_MODELS=gpt-4o-mini,claude-3-5-sonnet-20241022
```

**Example usage:**
```python
# Custom fallback chain
context = {
    "fallback_models": "gpt-4o-mini,claude-3-5-haiku-20241022"
}

# Or disable fallback
context = {"enable_fallback": false}
```

## Usage Patterns

### Pattern 1: Studio UI Configuration

1. Start server: `make dev`
2. Open Studio UI: http://localhost:8123
3. Select `agent_enhanced` or `agent_minimal` graph
4. Create Assistant
5. In configuration panel, adjust middleware settings:
   - Use dropdowns for model selection
   - Adjust sliders/inputs for limits
   - Toggle checkboxes for enable flags

All fields appear in the Studio UI with tooltips and descriptions.

### Pattern 2: Environment Variables

Set in `.env` file for deployment-wide configuration:

```bash
# .env

# Base configuration
SNOWFLAKE_AGENT_MODEL=claude-sonnet-4-5-20250929
SNOWFLAKE_AGENT_SNOWFLAKE_URI=sqlite:///test_snowflake.db

# Middleware configuration
SNOWFLAKE_AGENT_ENABLE_HITL=true
SNOWFLAKE_AGENT_MODEL_CALL_THREAD_LIMIT=15
SNOWFLAKE_AGENT_TOOL_CALL_THREAD_LIMIT=30
SNOWFLAKE_AGENT_SQL_QUERY_THREAD_LIMIT=15
SNOWFLAKE_AGENT_RETRY_MAX_RETRIES=5
SNOWFLAKE_AGENT_ENABLE_SUMMARIZATION=true
SNOWFLAKE_AGENT_SUMMARIZATION_TRIGGER_TOKENS=6000
SNOWFLAKE_AGENT_ENABLE_TODO=true
SNOWFLAKE_AGENT_ENABLE_FALLBACK=true
```

### Pattern 3: Runtime Context

Override per-conversation:

```python
from agent_snowflake import graph_enhanced

# Conservative limits for production
context = {
    "model_call_thread_limit": 5,
    "sql_query_run_limit": 3,
    "enable_hitl": True,
}

result = graph_enhanced.invoke(
    {"messages": [HumanMessage("Analyze customer data")]},
    config={"configurable": context}
)
```

### Pattern 4: Per-User Configuration

```python
def get_user_context(user_role: str) -> dict:
    """Get middleware config based on user role."""
    if user_role == "admin":
        return {
            "enable_hitl": False,  # Admins bypass approval
            "model_call_thread_limit": 50,
            "sql_query_thread_limit": 30,
        }
    elif user_role == "analyst":
        return {
            "enable_hitl": True,
            "model_call_thread_limit": 20,
            "sql_query_thread_limit": 15,
        }
    else:  # read-only users
        return {
            "read_only": True,
            "model_call_thread_limit": 10,
            "sql_query_thread_limit": 5,
        }

# Usage
context = get_user_context(current_user.role)
result = graph_enhanced.invoke(messages, config={"configurable": context})
```

## Helper Methods

### get_middleware_config()

Extract only middleware-specific fields:

```python
context = EnhancedContextSchema.from_env()
middleware_config = context.get_middleware_config()

print(middleware_config)
# {
#     "middleware_mode": "enhanced",
#     "enable_hitl": True,
#     "model_call_thread_limit": 10,
#     ...
# }
```

### to_dict()

Convert entire context to dictionary:

```python
context = EnhancedContextSchema.from_runnable_config(config)
config_dict = context.to_dict()

# Use for logging, serialization, etc.
logger.info(f"Context: {config_dict}")
```

## Validation and Defaults

### Zero Values (Disable Feature)

Setting limits to `0` disables that specific limit:

```python
context = {
    "model_call_thread_limit": 0,  # No thread limit
    "model_call_run_limit": 5,     # But still limit per run
}
```

### Boolean Flags

All `enable_*` flags default to `True` in enhanced mode. Set to `False` to disable:

```python
context = {
    "enable_summarization": False,
    "enable_todo": False,
    "enable_fallback": False,
}
```

### String Fields

- `middleware_mode`: `"enhanced"`, `"minimal"`, or `"none"`
- `model_call_exit_behavior`: `"end"` or `"error"`
- `tool_call_exit_behavior`: `"continue"`, `"end"`, or `"error"`
- `hitl_allowed_decisions`: Comma-separated values
- `fallback_models`: Comma-separated model names

## Troubleshooting

### Issue: "Field not found in Studio UI"

**Cause:** Using wrong graph variant

**Fix:** Ensure you selected `agent_enhanced` or `agent_minimal`, not `agent`

### Issue: "HITL not activating"

**Cause:** Either `enable_hitl=false`, `read_only=true`, or both

**Fix:** Set both:
```python
context = {
    "enable_hitl": True,
    "read_only": False
}
```

### Issue: "Middleware not applying"

**Cause:** Limits set to `0` or enable flags set to `False`

**Fix:** Check configuration:
```python
context = EnhancedContextSchema.from_env()
print(context.get_middleware_config())
```

### Issue: "Too many limits triggering"

**Cause:** Limits too aggressive for use case

**Fix:** Increase limits or disable specific middleware:
```python
context = {
    "model_call_thread_limit": 30,  # Increase
    "tool_call_thread_limit": 50,   # Increase
    "sql_query_thread_limit": 0,    # Disable
}
```

## Migration from Base ContextSchema

If you're currently using the base `ContextSchema` with `graph.py`:

### Option 1: Keep Using Base Schema

Continue using `agent` graph with `ContextSchema` - no changes needed.

### Option 2: Migrate to Enhanced Schema

1. Switch to `agent_enhanced` or `agent_minimal` graph
2. Update context references to `EnhancedContextSchema`
3. All base fields are preserved - backward compatible
4. Optionally configure new middleware fields

```python
# Before (graph.py with ContextSchema)
from agent_snowflake import graph, ContextSchema
context = ContextSchema.from_env()
result = graph.invoke(messages)

# After (graph2.py with EnhancedContextSchema)
from agent_snowflake import graph_enhanced, EnhancedContextSchema
context = EnhancedContextSchema.from_env()
result = graph_enhanced.invoke(messages)
```

All existing base fields work identically - only new middleware fields are added.

## Performance Impact

Adding middleware has minimal performance impact:

| Middleware | Latency Added | Notes |
|------------|---------------|-------|
| HITL | User-dependent | Blocks until approval |
| Call Limits | ~1ms | Just counter checks |
| Retry | Only on failure | 0ms for successful calls |
| Summarization | 2-3s when triggered | Only at threshold |
| Todo List | ~1ms | Adds one tool |
| Fallback | Only on failure | 0ms for successful calls |

**Total overhead:** < 5ms for normal operation (no failures, no summarization triggers).
